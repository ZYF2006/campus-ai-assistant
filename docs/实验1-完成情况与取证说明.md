## 三、类型系统建模（对应报告第 2 题）

全部定义位于 `packages/shared-types/src/index.ts`。

### （1）聊天角色 Role —— 字面量联合类型

```ts
export type Role = "system" | "user" | "assistant";
```

**为什么用联合类型而不是 enum**

- **零运行时开销**：`type` 在编译成 JavaScript 后会被完全擦除，不产生任何代码；而 `enum` 会生成一个反向映射对象（额外代码）。
- **无侵入性**：在 `verbatimModuleSyntax`、`const`、`declare` 等场景下，enum 容易产生出乎意料的行为，联合类型不会。
- **提示更友好**：悬停时直接显示 `"system" | "user" | "assistant"`，而不是枚举的数字引用。

### （2）聊天消息 ChatMessage

```ts
export interface ChatMessage {
  /** 消息唯一编号 */
  id: string;
  /** 消息角色，必须引用上面定义的 Role */
  role: Role;
  /** 消息正文 */
  content: string;
}
```

三个字段全部必填；`role` 引用 `Role`，因此写成 `"admin"`、`"User"` 等非法值会在编译期报错。

### （3）统一响应结构 ApiResponse\<T\>

```ts
export interface ApiResponse<T> {
  /** 业务状态码，0 表示成功 */
  code: number;
  /** 状态说明 */
  message: string;
  /** 接口返回的具体业务数据，其类型完全由 T 决定（不是 any） */
  data: T;
}
```

`T` 是类型「占位符」（形参），使用时才填入具体类型：`ApiResponse<ChatMessage>` 的 `data` 是一条消息，`ApiResponse<ChatMessage[]>` 的 `data` 是消息数组。因此**不需要**为单条消息和消息数组分别复制两套响应接口。

### （4）聊天请求与响应

```ts
export interface ChatRequest {
  messages: ChatMessage[];
}

export type ChatResponse = ApiResponse<ChatMessage>;
```

`ChatResponse` 用类型别名复用泛型接口，`data` 为一条 `ChatMessage`。

### （5）工具类型派生消息类型

```ts
/** 创建新消息时 id 由程序生成，调用者不需要提供 id */
export type NewChatMessage = Omit<ChatMessage, "id">;

/** 修改消息时只允许改 content，且 content 可以不提供 */
export type UpdateChatMessage = Partial<Pick<ChatMessage, "content">>;
```

| 工具类型 | 作用 | 本例用途 |
| --- | --- | --- |
| `Omit<T, K>` | 从类型中删除指定字段 | 删除 `id` 得到 `NewChatMessage` |
| `Pick<T, K>` | 从类型中选择指定字段 | 只保留 `content`，排除 `role` |
| `Partial<T>` | 把字段变为可选 | 让 `content` 可以不填 |
| `Readonly<T>` | 把字段变为只读 | （本实验未使用） |

### （6）进阶：自定义工具类型 ElementOf\<T\>（条件类型 + infer）

```ts
export type ElementOf<T> = T extends readonly (infer U)[] ? U : never;
```

**实现原理**：条件类型 `T extends readonly (infer U)[]` 中的 `infer U` 让 TypeScript 在匹配过程中「就地推断」出数组元素类型并绑定到 `U`；写成 `readonly ...[]` 是为了同时兼容可变数组与只读数组。传入非数组类型时得到 `never`。

| 输入 | 结果 |
| --- | --- |
| `ElementOf<ChatMessage[]>` | `ChatMessage` |
| `ElementOf<readonly string[]>` | `string` |
| `ElementOf<[number, string]>` | `number \| string` |
| `ElementOf<string>` | `never` |

### （7）进阶：类型守卫与判别联合

```ts
export function isRole(value: unknown): value is Role {
  return value === "system" || value === "user" || value === "assistant";
}

export function isChatMessage(value: unknown): value is ChatMessage {
  if (typeof value !== "object" || value === null) return false;
  const candidate = value as Record<string, unknown>;
  return (
    typeof candidate.id === "string" &&
    isRole(candidate.role) &&
    typeof candidate.content === "string"
  );
}
```

```ts
export type ChatEvent =
  | { status: "pending" }
  | { status: "success"; message: ChatMessage }
  | { status: "failure"; reason: string; retryable: boolean };

export function describeChatEvent(event: ChatEvent): string {
  switch (event.status) {
    case "pending":  return "正在思考…";
    case "success":  return `已收到回复：${event.message.content}`;
    case "failure":
      return event.retryable
        ? `发送失败：${event.reason}（可重试）`
        : `发送失败：${event.reason}`;
    default: {
      // 穷尽性检查：走到这里说明 ChatEvent 出现了尚未处理的新成员
      const exhaustive: never = event;
      return exhaustive;
    }
  }
}
```

`status` 是判别式，`switch` 后 TypeScript 能精确收窄到每个分支并校验字段齐全。`default` 分支的 `never` 兜底保证：**以后给 `ChatEvent` 加新成员，这里会立刻编译报错，不会漏处理**。

### （8）类型级自检（编译期断言）

文件末尾有一组断言，用于守住上面的类型约定（例如防止有人把 `role` 改成普通 `string`）：

```ts
type Equals<A, B> =
  (<T>() => T extends A ? 1 : 2) extends <T>() => T extends B ? 1 : 2 ? true : false;

type Assert<R extends true> = R;

type TypeAssertions = [
  Assert<Equals<ChatMessage["role"], Role>>,
  Assert<Equals<ApiResponse<number>["data"], number>>,
  Assert<Equals<NewChatMessage, { role: Role; content: string }>>,
  Assert<Equals<UpdateChatMessage, { content?: string }>>,
  Assert<Equals<ElementOf<ChatMessage[]>, ChatMessage>>,
  Assert<Equals<ElementOf<readonly string[]>, string>>,
  Assert<Equals<ElementOf<[number, string]>, number | string>>,
  Assert<Equals<ElementOf<string>, never>>,
  Assert<Equals<Extract<ChatEvent, { status: "success" }>["message"], ChatMessage>>,
];
```

> **踩坑记录（重要）**：最初这组断言写成 `declare const assertType: <A extends true>() => void` 再调用 `assertType<...>()`。
> 看起来运行时没有副作用，但 tsc **只擦除类型实参、保留那次函数调用**，于是编译产物里留下 `assertType()` —— 而该常量从未定义，**任何 import 这个包的模块一加载就抛错**。
> 改成纯类型写法（`Assert<R extends true> = R` 不产生任何语句）后，产物中 `assertType` 出现次数为 **0**。
> 这正说明了：**类型级代码也要检查它编译后到底生成了什么**。

## 四、全栈模拟聊天框架（对应报告第 3 题）

### 调用链

```text
App.vue（输入框）
    ↓ 调用
Pinia Store（stores/chat.ts）集中管理状态
    ↓ 调用
前端 API 模块（api/chat.ts）封装 HTTP 请求
    ↓ POST /api/chat（JSON）
Vite 开发代理（/api → http://localhost:3000）
    ↓
Express 后端（apps/server/src/index.ts）校验入参、构造模拟回复
    ↓ ChatResponse
Pinia Store 保存助手消息
    ↓
Vue 聊天界面渲染
```

本题后端**只返回模拟回复，不调用真实大模型**。

### （1）Express 模拟聊天接口（`apps/server/src/index.ts`）

```ts
import express from "express";
import type { ChatRequest, ChatMessage, ChatResponse } from "@campus-ai/shared-types";
import { isChatMessage } from "@campus-ai/shared-types";

const app = express();
const port = Number(process.env.PORT ?? 3000);

// 解析 JSON 请求体；设置大小上限，避免客户端提交过大的数据拖垮服务
app.use(express.json({ limit: "1mb" }));

// 健康检查：确认后端与 Vite 代理已经连通
app.get("/api/health", (_request, response) => {
  response.json({ message: "server is ready" });
});

function createAssistantMessage(content: string): ChatMessage {
  return {
    // crypto.randomUUID() 生成唯一消息编号
    id: crypto.randomUUID(),
    role: "assistant",
    content,
  };
}

app.post("/api/chat", (request, response) => {
  // Partial 表示请求中的字段可能缺失，因为外部数据不能完全信任
  const body = request.body as Partial<ChatRequest> | undefined;

  // 先确认 messages 确实是数组，再取得最后一条消息
  const lastMessage: unknown = Array.isArray(body?.messages)
    ? body.messages[body.messages.length - 1]
    : undefined;

  // 运行时校验：最后一条消息必须是合法的 ChatMessage
  if (!isChatMessage(lastMessage)) {
    const errorResponse: ChatResponse = {
      code: 1,                                  // 业务状态码非 0 表示失败
      message: "消息格式不合法",
      data: createAssistantMessage("消息格式不合法，请检查后重试"),
    };
    response.status(400).json(errorResponse);
    return;
  }

  const question = lastMessage.role === "user" ? lastMessage.content.trim() : "";

  if (!question) {                              // 空字符串表示没有收到有效问题
    const errorResponse: ChatResponse = {
      code: 1,
      message: "提交的消息不能为空",
      data: createAssistantMessage("请输入问题后再提交"),
    };
    response.status(400).json(errorResponse);
    return;
  }

  if (question.length > 1000) {                 // 超长输入直接拒绝
    const errorResponse: ChatResponse = {
      code: 1,
      message: "问题过长",
      data: createAssistantMessage("问题太长了，请精简到 1000 字以内"),
    };
    response.status(413).json(errorResponse);
    return;
  }

  // 创建格式符合 ChatResponse 的成功响应
  const successResponse: ChatResponse = {
    code: 0,                                    // 业务状态码 0 表示成功
    message: "ok",
    data: createAssistantMessage(
      `我收到了你的问题：“${question}”。这是后端返回的模拟回复。`,
    ),
  };

  response.json(successResponse);
});

app.listen(port, () => {
  console.log(`Server running at http://localhost:${port}`);
});
```

**要点**：

- `import type` 只导入类型，不产生运行时代码。
- `ChatRequest` 约束请求数据、`ChatResponse` 约束响应数据。
- `crypto.randomUUID()` 生成唯一消息编号。
- **TypeScript 类型检查不能代替运行时数据校验**：请求体来自外部，先按 `unknown` 处理，用类型守卫校验通过后才当作共享类型使用。

### （2）前端 API 模块（`apps/web/src/api/chat.ts`）

```ts
import type { ChatRequest, ChatResponse } from "@campus-ai/shared-types";

/**
 * 向后端发送聊天请求。
 *
 * 前端所有与后端交互的 HTTP 细节都集中在这个模块里：
 * 组件不直接编写 fetch，只调用这里导出的函数。
 */
export async function requestChat(request: ChatRequest): Promise<ChatResponse> {
  const response = await fetch("/api/chat", {
    method: "POST",
    body: JSON.stringify(request),
    headers: { "Content-Type": "application/json" },
  });

  // as ChatResponse 只做 TypeScript 类型断言，不会校验运行时数据
  const result = (await response.json()) as ChatResponse;

  // response.ok 检查 HTTP 状态码是否为 2xx
  // result.code 检查项目约定的业务状态码是否为 0
  if (!response.ok || result.code !== 0) {
    throw new Error(result.message);
  }

  return result;
}
```

### （3）Pinia 会话状态（`apps/web/src/stores/chat.ts`）

```ts
import type { ChatEvent, ChatMessage, NewChatMessage } from "@campus-ai/shared-types";
import { describeChatEvent } from "@campus-ai/shared-types";
import { defineStore } from "pinia";
import { computed, ref } from "vue";

import { requestChat } from "../api/chat";

/** 校园场景的示例问题，用于界面上的快捷提问 */
export const SUGGESTED_QUESTIONS = [
  "图书馆周末开放时间是几点？",
  "选修课什么时候可以退选？",
  "校园卡丢失了怎么补办？",
] as const;

/** 由「不含 id 的新消息」补齐 id，得到完整 ChatMessage */
function createMessage(message: NewChatMessage): ChatMessage {
  return { id: crypto.randomUUID(), ...message };
}

export const useChatStore = defineStore("chat", () => {
  // 关键知识点1：Store 中的响应式状态只定义一次，由所有组件共享读取
  const messages = ref<ChatMessage[]>([]);
  const isSending = ref(false);
  const errorMessage = ref<string | null>(null);

  const isEmpty = computed(() => messages.value.length === 0);

  // 把 Store 状态映射成判别联合 ChatEvent
  const currentEvent = computed<ChatEvent>(() => {
    if (errorMessage.value !== null) {
      return { status: "failure", reason: errorMessage.value, retryable: true };
    }
    if (isSending.value) return { status: "pending" };
    const latest = messages.value.at(-1);
    return latest ? { status: "success", message: latest } : { status: "pending" };
  });

  const statusText = computed(() => describeChatEvent(currentEvent.value));

  async function sendMessage(content: string): Promise<void> {
    const text = content.trim();

    // 关键知识点2：阻止空消息和重复提交
    if (!text || isSending.value) return;

    messages.value.push(createMessage({ role: "user", content: text }));
    isSending.value = true;
    errorMessage.value = null;

    try {
      // 关键知识点3：发送聊天记录快照，为以后多轮对话保留结构
      const result = await requestChat({ messages: [...messages.value] });
      messages.value.push(result.data);
    } catch (error: unknown) {
      // 关键知识点4：unknown 经过类型守卫后才能安全读取 message
      errorMessage.value =
        error instanceof Error ? error.message : "发送失败，请稍后重试";
    } finally {
      // 无论成功或失败，都必须恢复发送状态，否则输入框会一直禁用
      isSending.value = false;
    }
  }

  function clearMessages(): void {
    messages.value = [];
    errorMessage.value = null;
  }

  // 关键知识点5：只有在这里返回的内容，才能被 Vue 组件使用
  return { messages, isSending, errorMessage, isEmpty, statusText, sendMessage, clearMessages };
});
```

**Store 职责**：保存聊天记录 / 创建用户消息 / 调用聊天 API / 保存助手回复 / 管理发送状态与错误信息。

### （5）聊天页面（`apps/web/src/App.vue`）

```vue
<script setup lang="ts">
import { nextTick, ref, watch } from "vue";

import MessageItem from "./components/MessageItem.vue";
import { SUGGESTED_QUESTIONS, useChatStore } from "./stores/chat";

const chatStore = useChatStore();

/** 输入框内容 */
const inputText = ref("");
/** 消息区域 DOM 元素，用于新消息到达后滚动到底部 */
const messageArea = ref<HTMLElement | null>(null);

async function submitMessage(): Promise<void> {
  const content = inputText.value.trim();
  if (!content || chatStore.isSending) return;

  inputText.value = "";
  await chatStore.sendMessage(content);
}

async function askSuggestion(question: string): Promise<void> {
  if (chatStore.isSending) return;
  await chatStore.sendMessage(question);
}

// 消息数量变化后，自动把消息区滚动到最新一条
watch(
  () => chatStore.messages.length,
  async () => {
    await nextTick();
    const element = messageArea.value;
    if (element) element.scrollTop = element.scrollHeight;
  },
);
</script>

<template>
  <div class="chat">
    <header>
      <h1>校园 AI 助手</h1>
      <button
        v-if="chatStore.messages.length > 0"
        type="button"
        :disabled="chatStore.isSending"
        @click="chatStore.clearMessages()"
      >
        清空会话
      </button>
    </header>

    <!-- 只有消息区域滚动，输入框始终固定在底部 -->
    <section ref="messageArea" class="message">
      <p v-if="chatStore.isEmpty">请输入问题，开始与校园 AI 助手对话。</p>

      <button
        v-for="question in chatStore.isEmpty ? SUGGESTED_QUESTIONS : []"
        :key="question"
        type="button"
        class="suggestion"
        :disabled="chatStore.isSending"
        @click="askSuggestion(question)"
      >
        {{ question }}
      </button>

      <MessageItem
        v-for="message in chatStore.messages"
        :key="message.id"
        :message="message"
      />

      <p v-if="chatStore.isSending">正在回复…</p>
    </section>

    <p v-if="chatStore.errorMessage" class="error">{{ chatStore.errorMessage }}</p>

    <form @submit.prevent="submitMessage">
      <input
        v-model="inputText"
        type="text"
        maxlength="1000"
        autocomplete="off"
        placeholder="请输入问题"
        aria-label="聊天内容"
      />
      <button type="submit" :disabled="chatStore.isSending || !inputText.trim()">发送</button>
    </form>
  </div>
</template>
```

**布局关键点**：`.chat` 用 `display: flex; flex-direction: column`，`.message` 用 `flex: 1; min-height: 0; overflow-y: auto`。`min-height: 0` 是关键——没有它，flex 子项不会收缩，消息区无法滚动，输入框会被挤出可视区。

### （6）Vite 开发代理（`apps/web/vite.config.ts`）

  port: 5173,

    // 浏览器请求 /api 时由 Vite 转发给 Express，开发阶段无需在前端写死后端地址。
    // 页面必须通过 http://localhost:5173 访问，不能双击 HTML 使用 file://。

## 六、本地大模型的优点和缺点（对应报告第 1 题）

| 维度 | 优点 | 缺点 |
| --- | --- | --- |
| 数据隐私 | 数据完全不出本机，适合处理学生信息、成绩、内部文档等敏感内容 | 无 |
| 成本 | 无按 token 计费，可无限次调用；断网也能用 | 需要一次性硬件投入（显存/内存） |
| 延迟 | 本地推理无需跨网络往返，首 token 延迟稳定 | 消费级显卡上大参数模型推理慢，吞吐低 |
| 能力 | 小参数量模型（如 `qwen3:0.6b`）在 CPU 上即可运行 | 小模型的理解与推理能力明显弱于云端大模型，复杂任务容易答偏 |
| 部署 | 一条 `ollama pull` 即可用，接口与云端风格一致，便于切换 | 模型版本迭代需手动拉取，缺少云端那种自动升级 |
| 并发 | 单机可支撑少量并发 | 高并发场景需要多卡/多机，成本与运维复杂度陡增 |
| 可控性 | 可自行微调、可完全掌控推理参数与提示词 | 需要自己负责运维、监控、限流与安全防护 |

**技术选型结论**：本实验第 3 题属于「结构验证」性质，用 Mock 回复即可；真实上线时，
涉及**隐私/合规**的场景优先本地部署，追求**能力上限、弹性扩容**的场景选择云端 API。
工程上通常把两者抽象成同一套接口，通过配置切换，避免业务代码耦合具体供应商。

## 七、架构与安全边界分析（对应报告第 5 题）

### 1. 调用链

**本实验实现（Mock 阶段）**

```text
浏览器
  │  ① 用户输入问题
  ▼
App.vue ──②──► Pinia Store（stores/chat.ts）
                    │  ③ 组装 ChatRequest（含历史消息快照）
                    ▼
              api/chat.ts ──④ POST /api/chat（JSON）
                    │
                    ▼
         Vite 开发代理（/api → localhost:3000）   ← 仅开发期存在
                    │
                    ▼
      Express 后端（apps/server/src/index.ts）
                    │  ⑤ 运行时校验 → 构造模拟回复
                    ▼
              ChatResponse ──⑥──► Pinia Store ──⑦──► Vue 界面渲染
```

**演进到真实大模型后**

```text
浏览器 → Vue → Pinia → api/chat.ts
                          │  POST /api/chat
                          ▼
                   Express 后端（唯一持有 API Key 的一层）
                          │  ⑧ 组装提示词 + 调用大模型
                          ▼
              本地 Ollama / 云端大模型服务
                          │  ⑨ 模型输出
                          ▼
                   Express 后端（输出处理）
                          │  ChatResponse
                          ▼
                   Pinia Store → Vue 界面
```

### 2. 安全边界

| 边界 | 风险 | 本项目做法 / 应遵循原则 |
| --- | --- | --- |
| **API Key** | 写进前端代码或提交到 Git，等于公开泄露 | API Key **只能存后端环境变量**（`apps/server/.env`）。`.gitignore` 已忽略 `.env` / `.env.*`，仅提交不含密钥的 `.env.example`。前端永远不接触密钥。 |
| **输入校验** | 前端可被绕过，攻击者直接构造请求；超长输入可拖垮服务 | **不信任任何外部输入**。后端把请求体当 `unknown`，用 `isChatMessage` 类型守卫校验后才使用；`express.json({ limit: "1mb" })` 限制体积；问题超过 1000 字返回 413。 |
| **输出处理** | 模型输出可能含 `<script>` 等恶意内容，导致 XSS | 前端一律使用**文本插值** `{{ message.content }}`，Vue 会自动转义；**绝不使用 `v-html`**，因此不可信内容无法变成可执行脚本。 |
| **错误信息** | 直接把数据库/服务端堆栈返回给前端会泄露内部结构 | 错误响应只返回**业务化文案**（如"消息格式不合法"）与业务状态码，不暴露堆栈与内部路径。 |
| **业务状态码与 HTTP 状态码** | 只靠 HTTP 200 判断成功，会把业务失败当成功 | 两层都要判：前端 `if (!response.ok \|\| result.code !== 0) throw`，HTTP 状态码与业务 `code` 分别表达传输层与业务层结果。 |
| **工具调用权限**（后续 Agent 阶段） | 大模型若可直接执行工具/命令，可能被提示词注入利用，越权操作文件或数据库 | 应遵循**最小权限**：工具白名单化、参数做服务端校验、危险操作二次确认、按用户身份鉴权、全程审计日志；**绝不让模型直接拼接 SQL 或 Shell**。 |
| **跨域与代理** | 开发代理 `changeOrigin` 仅用于本地；生产环境若直连会暴露后端端口 | 生产环境应由同一网关/反向代理统一暴露，前端与后端同源；后端不直接对公网开放。 |
| **依赖与供应链** | 依赖被投毒或存在已知漏洞 | 提交 `pnpm-lock.yaml` 锁定版本；pnpm 默认禁止依赖执行安装脚本（本项目仅白名单放行 `esbuild`），减少供应链攻击面。 |

### 3. 「类型先行」工作流的落地

1. **先定义类型**：在 `packages/shared-types` 定义 `Role` / `ChatMessage` / `ApiResponse<T>` / `ChatRequest` / `ChatResponse`。
2. **再写实现**：前端与后端都从共享包导入类型，双方契约由同一份定义保证。
3. **编译校验**：`pnpm typecheck` / `vue-tsc` 在构建前就暴露参数类型错误、字段缺失、方法不存在等问题。
4. **人工审查**：用 `git diff` 逐行确认 AI 改动范围，确认没有越界修改业务逻辑。
5. **运行时兜底**：类型在运行时会被擦除，因此**关键边界必须补运行时校验**（本项目的 `isChatMessage`）。

## 十、常见问题

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 页面一直显示"正在回复…" | 后端没启动，或接口分支没有走到 `response.json(...)` | 先访问 `http://localhost:3000/api/health` 确认后端已起 |
| 控制台 `file:///api/chat` | 用 `file://` 打开了 HTML | 改为访问 `http://localhost:5173` |
| 端口被占用 | 3000 或 5173 上有旧进程 | 关闭旧进程后重新 `pnpm dev` |
| `pnpm install` 报依赖脚本被阻止 | pnpm 默认禁止依赖执行安装脚本 | 在 `pnpm-workspace.yaml` 的 `allowBuilds` 中按需白名单放行 |
